## CHUNK 1: Qdrant API Key Leak Scrub from Public Repo Scripts

### Context
The rag-gateway-mini repo is a PUBLIC GitHub repo (figulazmi/rag-gateway-mini).
Six tracked files embedded the Qdrant api-key as an inline string literal,
leaking the credential to anyone who clones or browses the repo on GitHub.

### Problem
Hardcoded key 0aa9f... appeared in: scripts/eval-retrieval-quality.py (line 54,
Python const), scripts/qdrant-graph.sh (line 26) and scripts/qdrant-visualize.sh
(line 23) as bash vars, scripts/qdrant-mcp-server-v2/qdrant-mcp-server-v2.js
(line 9) as JS const, scripts/rag-capture-v2/test-rag-v2.sh (line 481) inside an
echo documentation string, and .claude/settings.local.json (line 106) as a Bash
permission allowlist entry. First committed in 5762b57, 0db0f00, e1b01a0.

### Solution
Replaced every literal with a per-language env-var read that fails fast when
unset. Python uses os.environ.get + raise SystemExit. Bash uses the parameter
expansion QDRANT_API_KEY="${QDRANT_API_KEY:?msg}" which aborts immediately under
set -euo pipefail. Node reads process.env.QDRANT_API_KEY and process.exit(1) if
missing. The doc string became a <YOUR_KEY> placeholder. The Claude permission
allowlist entry that pre-exported the literal key was deleted outright, since
scripts now pull from env. Runtime UX: source ~/.config/qdrant-knowledge.env
once per shell, then scripts work unchanged. Error path: helpful message
pointing at the env file, no stack trace.

### Key Facts
- Public-repo secret leak is only half-fixed by source scrub — git history still retains the literal key until filter-repo plus force push is executed
- Bash parameter expansion ${VAR:?msg} combined with set -euo pipefail produces a clean fail-fast with custom error text and exit code 1
- Python os.environ.get returns None when unset — pair with if not VAR raise SystemExit(msg) to avoid urllib sending a None header later
- Node process.env.VAR returns undefined when unset — guard with if (!VAR) console.error + process.exit(1) before any fetch call
- push-to-qdrant.sh already sources ~/.config/qdrant-knowledge.env (chmod 600, outside repo) — capture flow rag add plus rag merge unaffected since they never hit Qdrant
- Only direct-query scripts (eval, graph, visualize, mcp-server) now require source of the env file per shell session
- Claude Code settings.local.json is git-tracked on this repo — permission allowlist entries containing literal secrets are leaks too
- Verification: git grep of the literal key returns empty, unset VAR then run script returns the custom error, sourced env runs script normally

### Code / Commands
```python
# Python pattern (eval-retrieval-quality.py)
import os
QDRANT_API_KEY = os.environ.get("QDRANT_API_KEY")
if not QDRANT_API_KEY:
    raise SystemExit("QDRANT_API_KEY env var not set. Source ~/.config/qdrant-knowledge.env first.")
```

```bash
# Bash pattern (qdrant-graph.sh, qdrant-visualize.sh) — needs set -euo pipefail
QDRANT_API_KEY="${QDRANT_API_KEY:?QDRANT_API_KEY not set (source ~/.config/qdrant-knowledge.env)}"
```

```javascript
// Node pattern (qdrant-mcp-server-v2.js)
const QDRANT_API_KEY = process.env.QDRANT_API_KEY;
if (!QDRANT_API_KEY) {
  console.error("QDRANT_API_KEY env var not set");
  process.exit(1);
}
```

### Caveats
Source scrub alone does NOT remove the key from GitHub history — clones of any
prior commit still expose it. Full remediation requires: (1) rotate key on VM B1
Qdrant container, (2) git filter-repo --replace-text to rewrite history, (3)
force push to origin, (4) update ~/.config/qdrant-knowledge.env and VM B1
/opt/rag-gateway/appsettings.Production.json with the rotated key. Until step 1
is done, treat the leaked key as compromised even after this commit.
