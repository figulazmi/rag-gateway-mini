## CHUNK 1: Qdrant 401 Unauthorized on Local dotnet run

### Context

rag-gateway-mini is an ASP.NET Core 9 RAG gateway running locally via `dotnet run`
during development. It connects to Qdrant at 192.168.18.169:6333 (VM B1 homelab).
QdrantVectorSearchClient adds `api-key` header only when QdrantApiKey is non-empty.

### Problem

Hitting POST /rag/search returns HTTP 500. App logs show:
`System.Net.Http.HttpRequestException: Response status code does not indicate success: 401 (Unauthorized)`
at QdrantVectorSearchClient.ExecuteSearchAsync line 75.
Root cause: `appsettings.json` has `"QdrantApiKey": ""` — empty string.
Since the value is empty, the `api-key` header is never added to the HTTP request.

### Solution

Set QdrantApiKey via .NET User Secrets for local development — never hardcode secrets
in appsettings.json which is committed to git.

```bash
cd src
dotnet user-secrets set "RagGateway:QdrantApiKey" "<actual-key>"
```

User Secrets are automatically loaded in Development environment. No code change needed.

### Key Facts

- QdrantVectorSearchClient only adds api-key header when QdrantApiKey is non-empty (line 20-21)
- appsettings.json has QdrantApiKey as empty string by design — secrets must not be committed
- Qdrant returns 401 when api-key header is missing and auth is enabled on the server
- Use `dotnet user-secrets set` for local dev secrets — loaded automatically in Development env
- Production key lives at /opt/homelab/ai-stack/rag-gateway-mini/appsettings.Production.json (outside repo)

### Caveats

The appsettings.Production.json.template in the repo previously contained the real API key.
This is a security risk if the repo is public. Rotate the Qdrant API key and replace the
template value with a placeholder like `YOUR_QDRANT_API_KEY_HERE`.

## CHUNK 2: Docker Volume Mount Path Mismatch Causing 500 on VM B1

### Context

rag-gateway-mini runs as a Docker container on VM B1 (192.168.18.169).
Production secrets are stored outside the repo in a separate appsettings.Production.json
file, mounted into the container as a read-only volume via docker-compose.yml.

### Problem

After `docker compose up -d --build`, the /rag/search endpoint returns HTTP 500.
Root cause: docker-compose.yml volume mount pointed to `/opt/rag-gateway/appsettings.Production.json`
but the actual file existed at `/opt/homelab/ai-stack/rag-gateway-mini/appsettings.Production.json`.
The container started without the config file, causing missing QdrantApiKey (empty/null).

### Solution

Update the volume mount path in docker-compose.yml to match the actual folder structure on VM B1:

```yaml
# Before (wrong path)
volumes:
  - /opt/rag-gateway/appsettings.Production.json:/app/appsettings.Production.json:ro

# After (correct path)
volumes:
  - /opt/homelab/ai-stack/rag-gateway-mini/appsettings.Production.json:/app/appsettings.Production.json:ro
```

Then on VM B1: git pull origin main, then docker compose up -d --build.

### Key Facts

- docker-compose.yml volume mount path must exactly match the file path on the VM host
- appsettings.Production.json lives at /opt/homelab/ai-stack/rag-gateway-mini/ (repo root, outside src/)
- ASPNETCORE_ENVIRONMENT=Production is set in docker-compose.yml — app loads appsettings.Production.json
- Container mounts the file as read-only (:ro) — never write secrets inside the container image
- Redeploy command: `cd /opt/homelab/ai-stack/rag-gateway-mini/src && docker compose up -d --build`

### Caveats

After changing docker-compose.yml, always git pull on the VM before running docker compose up,
otherwise the container uses the old compose file with the wrong volume path.
