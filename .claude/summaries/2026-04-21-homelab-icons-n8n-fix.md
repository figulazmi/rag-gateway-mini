## CHUNK 2: n8n WEBHOOK_URL stale IP after VM migration

### Context
VM B1 homelab was migrated and its LAN IP changed from 192.168.18.169 to 192.168.18.199. The n8n service in /opt/homelab/ai-stack/qdrant/docker-compose.yml had a hardcoded WEBHOOK_URL pointing to the old IP.

### Problem
n8n WEBHOOK_URL=http://192.168.18.169:5678 used the old VM IP after migration. This caused: workflow thumbnail previews to fail (client-side requests routed to wrong host), n8n instability visible in uptime-kuma (35-43% downtime on Apr 19-20), and webhook URLs generated by n8n to be unreachable.

### Solution
Edit docker-compose.yml to change WEBHOOK_URL from 192.168.18.169 to 192.168.18.199. Redeploy with: cd /opt/homelab/ai-stack/qdrant && docker compose up -d --no-deps n8n. The --no-deps flag is required because n8n depends_on qdrant which is managed by a different compose project and conflicts on container name if recreated.

### Key Facts
- n8n WEBHOOK_URL controls the base URL n8n uses for webhook links and internal URL generation
- After VM IP change, all hardcoded IPs in docker-compose env vars must be updated
- docker compose up -d n8n fails if qdrant container name conflicts; use --no-deps to skip dependency recreation
- Uptime-kuma icon cache: /app/data/icon/ dir does not exist if no icons configured; icons for private IPs need manual emoji setup in UI
- Uptime-kuma fetches icons via external DuckDuckGo service which cannot resolve 192.168.x.x private IPs
### Code
```bash
# Fix WEBHOOK_URL
sed -i 's|WEBHOOK_URL=http://192.168.18.169:5678|WEBHOOK_URL=http://192.168.18.199:5678|' \
  /opt/homelab/ai-stack/qdrant/docker-compose.yml

# Redeploy n8n only
cd /opt/homelab/ai-stack/qdrant
docker compose up -d --no-deps n8n
```

## CHUNK 3: homelab service icons missing and n8n workflow thumbnails broken

### Context
VM B1 (192.168.18.199) runs 10 Docker services monitored by uptime-kuma. After a VM IP migration (old: 192.168.18.169), two visual issues surfaced: no icons shown on uptime-kuma dashboard or browser tabs, and n8n workflow thumbnails missing from workflow list.

### Problem
1. Uptime-kuma shows no icons for any monitor. Root cause: uptime-kuma v1 uses DuckDuckGo external favicon service which cannot resolve private IPs (192.168.18.199). No /app/data/icon/ cache dir existed. Fix: manually set emoji icons per monitor in uptime-kuma UI.
2. n8n workflow thumbnail previews blank. Root cause: WEBHOOK_URL=http://192.168.18.169:5678 used stale VM IP. n8n generates internal URLs with this value; client-side thumbnail requests routed to wrong host.
3. n8n showed 35% uptime window in uptime-kuma due to crashes on Apr 19-20, caused by wrong WEBHOOK_URL.

### Solution
Fixed WEBHOOK_URL in /opt/homelab/ai-stack/qdrant/docker-compose.yml (192.168.18.169 -> 192.168.18.199). Redeployed with docker compose up -d --no-deps n8n. Manual step remaining: set emoji icons per monitor in uptime-kuma UI at port 3001. Browser cache must be cleared after (Ctrl+Shift+Delete) to flush cached 404 favicon responses.

### Key Facts
- uptime-kuma icon cache path: /app/data/icon/ - absence confirms no icons ever fetched
- uptime-kuma uses DuckDuckGo (https://icons.duckduckgo.com/ip3/{hostname}.ico) for auto-favicon; private IPs always fail
- n8n --no-deps flag needed when redeploying: docker compose up -d --no-deps n8n (qdrant conflict)
- After VM IP migration, grep all docker-compose env vars for old IP: grep -r "192.168.18.169" /opt/homelab/
- Browser caches favicon 404 responses; must clear cache after fixing favicon source
### Code
```bash

# Redeploy n8n only (skip conflicting qdrant dependency)
cd /opt/homelab/ai-stack/qdrant && docker compose up -d --no-deps n8n
```
