## CHUNK 1: MCP Server Upgrade to knowledge_v2 Hybrid Search RRF

## CHUNK 1: MCP Server Upgrade From knowledge to knowledge_v2 With Hybrid Search

### Context

The qdrant-knowledge MCP tool on VM B1 serves RAG retrieval for Claude Code sessions
across two projects (homelab, petrochina-eproc). It was consuming the dense-only
"knowledge" collection using the unnamed-vector /points/search endpoint. The
"knowledge_v2" collection already existed with 150 points indexed using hybrid
search (named dense 768-dim + sparse BM25 djb2), but the MCP was not targeting it.

### Requirements

- Switch MCP target to "knowledge_v2" collection.
- Implement hybrid query at search time: dense + sparse RRF fusion.
- Sparse vector algorithm must match index-time djb2 hash exactly.
- Preserve all existing logic: RAG-FIRST enforcement, retry, NOT FOUND gate.

### Architecture Decision

Use client-side djb2 hash in the MCP JS for sparse vector generation, identical to
migrate-to-hybrid.py. This is required because knowledge_v2 was indexed using
client-side djb2, not Qdrant server-side BM25 model. Using the wrong tokenizer at
query time produces mismatched sparse indices and degrades retrieval. Hybrid fusion
uses Qdrant RRF via /points/query endpoint with two prefetch legs.

### Implementation

File updated: /opt/mcp-servers/qdrant-knowledge/qdrant-mcp-server.js on VM B1.
Key changes from v1.0.0 to v2.0.0: COLLECTION constant changed to "knowledge_v2";
djb2Sparse() function added; searchQdrant() switched to /points/query with two
prefetch entries (dense and sparse) fused server-side with RRF; searchMode
"hybrid-rrf" added to log events.

### Key Facts

- knowledge_v2 schema: dense "dense" (768-dim, Cosine) + sparse "sparse" (IDF modifier).
- Sparse vectors in knowledge_v2 were built using client-side djb2, NOT Qdrant server-side BM25.
- djb2 algorithm: h = 5381; for each char: h = (((h << 5) + h) + charCode) & 0x7FFFFFFF.
- Hybrid query endpoint is /collections/{name}/points/query with prefetch array + fusion rrf.
- MCP process is spawned per-connection by claude-mcp-connect.ps1 - no manual restart needed.
- Backup saved at ~/qdrant-mcp-server.js.bak on VM B1 before overwriting.

### Code / Commands

```javascript
function djb2Sparse(text) {
  const tokens = text.toLowerCase().match(/[a-z0-9]+/g) || [];
  const tf = {};
  for (const token of tokens) {
    let h = 5381;
    for (const ch of token) {
      h = (((h << 5) + h) + ch.charCodeAt(0)) & 0x7FFFFFFF;
    }
    tf[h] = (tf[h] || 0) + 1;
  }
  return { indices: Object.keys(tf).map(Number), values: Object.keys(tf).map(i => tf[i]) };
}
```

## CHUNK 2: rag-knowledge-capture-cli Skill v2 Migration to rag CLI Pipeline

## CHUNK 2: rag-knowledge-capture-cli Skill Updated to Use rag CLI Pipeline

### Context

The rag-knowledge-capture-cli skill is a Claude Code slash command that captures
session knowledge into Qdrant-ready chunks. The skill previously instructed Claude
to write .md files directly using the Write tool, bypassing rag_capture.py entirely.
The rag CLI (rag_capture.py) was installed as a global tool but never used by the skill.

### Requirements

- Claude must call "rag add" via Bash for each chunk instead of using Write tool.
- Claude must call "rag merge" after all chunks to produce final .md file.
- Frontmatter must be generated by rag_capture.py from CLI flags, not written manually.
- Collection reference must be updated from "knowledge" to "knowledge_v2".

### Architecture Decision

Remove direct file writing from skill responsibility entirely. rag_capture.py is the
single source of truth for frontmatter schema, draft lifecycle, and SESSION METADATA
generation. This ensures rag list/status/remind reflect real session state and the
draft folder is usable for incremental multi-session capture.

### Implementation

Updated file: ~/.claude/commands/rag-knowledge-capture-cli.md. Changes:
- AUTO-SAVE BEHAVIOR section: replaced Write tool instructions with "rag add" heredoc
  pattern and "rag merge --output" command.
- FRONTMATTER SCHEMA section: replaced YAML template with rag CLI flags table.
- SESSION METADATA section: noted it is auto-generated by "rag merge", not written manually.
- HARD RULES: added "NEVER use Write tool", "NEVER write frontmatter manually",
  updated auto-save rule to reference rag CLI.
- EXAMPLE section: replaced .md output example with actual rag add + rag merge
  Bash commands.
- Collection references updated from "knowledge" to "knowledge_v2" throughout.
- Added MIGRATION.md to .claude/skills/rag-knowledge-capture-cli/ with before/after
  comparison, full flow diagram, and key file locations.

### Key Facts

- Active skill file is ~/.claude/commands/rag-knowledge-capture-cli.md, not SKILL.md in repo.
- SKILL.md in repo is the source/reference copy - must be kept in sync manually.
- rag_capture.py drafts go to ~/scripts/.rag_drafts/, not .claude/summaries/ directly.
- "rag merge" produces the final file in .claude/summaries/ and prints push reminder.
- Collection target comes from ~/.rag_config.json, not hardcoded in the skill.
