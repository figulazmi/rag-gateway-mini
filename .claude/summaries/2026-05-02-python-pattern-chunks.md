## CHUNK 1: Python argparse subcommand CLI pattern
<!-- rag_chunk_meta chunk_type=pattern tags=[homelab, vm-b1, python, cli, argparse, pattern, automation] -->

### Target Files
Python CLI scripts that expose multiple commands, including tools under `~/scripts/` and repository `scripts/*.py` utilities.

### Context
Use this pattern when a Python tool needs named subcommands such as `add`, `status`, `push-pending`, or `resume`. The goal is a predictable command line contract that is easy for automation and Claude Code sessions to call.

### Problem
Ad hoc `sys.argv` parsing makes subcommands hard to validate, hard to document, and easy to break when adding boolean flags or required arguments.

### Solution
Create a top-level `argparse.ArgumentParser`, add subcommands with `add_subparsers(dest="command", required=True)`, and define each command with `subparsers.add_parser("name")`. Put command-specific flags on the returned parser using `add_argument`. Use `choices` for constrained values and `action="store_true"` for booleans.

### Key Facts
- `add_subparsers(dest="command", required=True)` forces the user to choose a subcommand.
- `subparsers.add_parser("status")` creates one isolated parser per command.
- Use `choices=[...]` for enum-like inputs and `action="store_true"` for boolean flags.
- Dispatch with `if args.command == "status":` or a function map after `parse_args()`.

### Code
```python
parser = argparse.ArgumentParser(prog="tool")
subparsers = parser.add_subparsers(dest="command", required=True)

status = subparsers.add_parser("status")
status.add_argument("--verbose", action="store_true")

add = subparsers.add_parser("add")
add.add_argument("--type", choices=["debug", "pattern"], required=True)

args = parser.parse_args()
```

## CHUNK 2: Python dataclass schema pattern
<!-- rag_chunk_meta chunk_type=pattern tags=[homelab, vm-b1, python, dataclass, schema, pattern, automation] -->

### Target Files
Python modules that define structured records or report DTOs, especially eval scripts, RAG tooling, and automation utilities under `scripts/*.py` or `~/scripts/**/*.py`.

### Context
Use this pattern when Python code needs lightweight typed containers for configuration, eval cases, report rows, or parsed metadata. Dataclasses keep the schema explicit without introducing a heavy dependency.

### Problem
Plain dictionaries hide required fields, make defaults inconsistent, and make serialization logic repetitive. Mutable defaults such as `[]` also create shared state bugs across instances.

### Solution
Use `@dataclass(slots=True)` for compact structured records. Use `field(default_factory=list)` or `field(default_factory=dict)` for mutable defaults. Use `asdict()` when writing JSON reports. Add `__post_init__` only for invariants that must always hold after construction.

### Key Facts
- Use `field(default_factory=list)` instead of `items: list = []` to avoid shared mutable defaults.
- `asdict(instance)` converts nested dataclasses into JSON-ready dictionaries.
- `slots=True` reduces memory and prevents accidental new attributes.
- `__post_init__` is the right place to validate derived invariants after dataclass initialization.

### Code
```python
from dataclasses import asdict, dataclass, field

@dataclass(slots=True)
class EvalCase:
    query: str
    project: str
    gold_keywords: list[str] = field(default_factory=list)

    def __post_init__(self) -> None:
        if not self.query.strip():
            raise ValueError("query is required")

payload = asdict(EvalCase(query="status command", project="homelab"))
```
