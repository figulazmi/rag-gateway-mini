## CHUNK 1: VM105 n8n webhook auth hardening
<!-- rag_chunk_meta chunk_type=debug tags=[homelab, vm-b1, n8n, qdrant, webhook-auth, vm105] -->

### Context
VM105 runs the restored homelab RAG stack with n8n, Qdrant, Ollama, and rag-gateway services. The knowledge ingest pipeline uses rag-tools source files from the local device and deploys workflow JSON to the server.
### Problem
The old public n8n webhook path was predictable, and n8n returned empty HTTP 200 responses when workflow nodes failed. The restored VM105 workflow also failed because n8n 2.15 blocked workflow node access to environment variables needed for the Qdrant API key.
### Solution
The n8n workflow was regenerated with a secret-bearing path based on N8N_WEBHOOK_SECRET, then imported and activated on VM105. The n8n container was recreated with N8N_BLOCK_ENV_ACCESS_IN_NODE=false so HTTP nodes can read QDRANT_API_KEY. push-to-qdrant.sh now requires N8N_WEBHOOK_SECRET, sends X-Webhook-Secret, requires response JSON containing status ok, writes an audit log entry, and hard-aborts only on cosine gate failure status 1.
### Key Facts
- VM105 old public path /webhook/knowledge-ingest returned 404 after hardening.
- Authenticated push-to-qdrant.sh smoke test returned HTTP 200 with status ok and increased Qdrant points_count from 368 to 369.
- The audit log ~/.rag_audit.log increased from 2 to 3 lines after the accepted upsert.
- verify_embed_cosine.py passed for vm105-auth-test-20260430-chunk-1 after the smoke push.
